# LANS-AFS-SIM 소스 코드 상세 설명

> 확인 기준: 현재 폴더의 C 소스, 2026-08-11
> 이 문서는 코드에서 직접 확인한 구현과 하드코딩을 기준으로 한다. 소스만으로 확정할 수 없는 AFS 규격의 의도는 추측하여 단정하지 않는다.

## 먼저 알아야 할 위성·신호 기초

### 위성항법은 무엇을 보내는가

항법 위성은 자기 PRN, 송신 시각, 궤도 파라미터, 위성 시계 보정값을 반복 송신한다. 수신기는 여러 위성 신호의 도착 시간을 측정해 의사거리(pseudorange)를 만들고, 보통 4개 이상 위성으로 수신기 3차원 위치와 수신기 시계 오차를 함께 계산한다.

### PRN, chip, symbol, I/Q의 차이

- 데이터 bit는 항법 payload의 0/1이다.
- 채널 부호 symbol은 CRC·LDPC 후 실제 data 채널에 실리는 0/1이다.
- chip은 위성을 구분하는 PRN 확산 코드의 더 빠른 단위다.
- I/Q sample은 확산과 반송파 회전까지 끝난 기저대역 파형의 수치 샘플이다.

이 코드의 AFS symbol 하나는 2 ms다. 그동안 I 채널은 2046 chip을 진행한다. 12 MHz 출력이라면 한 symbol은 24,000 complex I/Q sample에 걸쳐 나타난다. 따라서 내부 배열의 “1 symbol=0/1 한 개”는 맞지만 최종 파일의 “1 symbol=sample 한 개”는 아니다.

### I와 Q

- I(data) 채널: PRN code × AFS navigation symbol
- Q(pilot) 채널: PRN code × secondary code × tertiary code

두 성분을 90도 직교 성분으로 합쳐 complex baseband I/Q를 만든다.

## 결론

LANS-AFS-SIM-main은 달 표면의 특정 수신 지점에서 수신되는 AFS 위성 신호를 소프트웨어로 합성하여, SDR에서 재생 가능한 복소 I/Q 기저대역 샘플 파일을 만드는 프로그램입니다.

단순한 항법 데이터 생성기가 아니라 다음 요소를 함께 시뮬레이션합니다.
```text
- 달 중심 위성 궤도
- 달 표면 수신기 위치
- 위성 가시성
- 위성별 전파 지연과 의사거리
- 위성 움직임에 따른 도플러
- 위성별 확산 코드
- AFS 항법 프레임
- CRC·BCH·LDPC·인터리빙
- 거리 기반 신호 세기
- 열잡음과 2비트 ADC 양자화
- 여러 위성 신호의 합성
- SDR 송출용 I/Q 파일
```
핵심 실행 코드는 LANS-AFS-SIM-main/afs_sim.c:943입니다.

## 1. 입력 궤도와 수신기 위치

### 위성 궤도

프로그램은 최대 12개 위성을 처리합니다.

#define MAX_SAT (12)

알마낙에서 다음 값을 읽습니다.
```text
- 위성 PRN
- 이심률
- 궤도 적용 시각
- 궤도 경사각
- 장반경의 제곱근
- 승교점 적경
- 근지점 인수
- 평균 근점각
- 위성 시계 보정값 af0, af1
- GPS week
```
구현은 LANS-AFS-SIM-main/afs_sim.c:651에 있습니다.

기본 파일은 LANS-AFS-SIM-main/default_almanac.txt입니다. 기본 알마낙은 실제 운용 궤도라기보다는 12개 위성을 배치한 시뮬레이션 시나리오에 가깝습니다.

궤도 계산에는 지구 중력상수가 아니라 달 중력상수와 달 반경을 사용합니다.

#define GM_MOON 4.9028e12
#define R_MOON 1737.4e3

따라서 이 프로그램은 일반적인 GPS 위성 시뮬레이터를 달 궤도 항법 시스템에 맞게 변경한 구조입니다.

### 수신기 위치

-l latitude:longitude:height로 달 표면의 수신 위치를 지정합니다.

지정하지 않으면 다음 위치가 사용됩니다.

- 위도: 남위 89.66°
- 경도: 동경 129.20°
- 고도: 100 m
- 코드 주석상 위치: Shackleton crater

위치는 LANS-AFS-SIM-main/afs_sim.c:1047에서 결정되고, 달을 완전한 구로 가정하여 직교좌표로 변환합니다.

지구 GNSS에서 사용하는 타원체나 지형 모델은 없습니다.

## 2. 위성 위치와 가시성 계산

satpos()는 케플러 방정식을 반복 계산하여 시각별 위성 위치와 속도를 구합니다.

구현: LANS-AFS-SIM-main/afs_sim.c:555

계산 과정은 다음과 같습니다.

1. 알마낙 기준 시각에서 경과시간 계산
2. 평균 근점각 계산
3. 반복법으로 이심 근점각 계산
4. 진근점각과 궤도 반경 계산
5. 달 중심 좌표계의 위성 위치·속도 계산
6. af0 + dt × af1로 위성 시계 오차 계산

위성-수신기 벡터를 지역 North-East-Up 좌표로 바꾸고, 고도가 0°보다 큰 위성만 채널에 할당합니다.

즉, 시작 시각에 달의 지평선 아래에 있는 위성은 신호 합성에서 제외됩니다.

다만 가시성은 시작할 때 한 번만 판정합니다. 시뮬레이션 도중 위성이 떠오르거나 지는 상황에 대한 채널 추가·제거는 없습니다.

### I 채널 확산 코드

I 채널 코드는 두 개의 11단 LFSR에서 생성한 시퀀스를 PRN별 지연값으로 조합합니다.

구현: LANS-AFS-SIM-main/afs_sim.c:277

PRN 1~210에 대응하는 지연 테이블을 가지고 있지만, 이 시뮬레이터에서는 최대 12개만 사용합니다.

### Q 채널 확산 코드

Q 코드는 GPS L1C 파일럿 코드와 유사하게 다음 방식으로 생성합니다.

- 길이 10223 Legendre sequence 생성
- PRN별 Weil index 적용
- PRN별 위치에 7개 chip 삽입
- 최종 길이 10230 chip 생성

구현: LANS-AFS-SIM-main/afs_sim.c:353

### Secondary와 tertiary 코드

Q 채널에는 두 계층의 오버레이 코드가 추가됩니다.

- Secondary code: 4 chip, 주기 8 ms
- Tertiary code: 1500 chip, 주기 12초

Tertiary 코드는 008_Weil1500hex210prns.txt에서 PRN별로 읽습니다.

따라서 Q 파일럿 채널의 전체 코드 상태도 I 채널의 12초 항법 프레임과 맞춰집니다.

## 5. 의사거리와 도플러

computeRange()는 다음을 계산합니다.

- 수신 시각에서의 위성 위치
- 위성까지 전파되는 시간
- 전파 시간만큼 과거로 외삽한 송신 시각의 위성 위치
- 위성 시계 오차가 반영된 의사거리
- 시선 방향 상대속도

구현: LANS-AFS-SIM-main/afs_sim.c:829

매 0.1초마다 새 의사거리를 계산하고, 이전 값과의 차이로 의사거리 변화율을 구합니다.

rhorate = (rho1.range - rho0.range) / dt;
f_carr = -rhorate / wavelength;

이 값으로 다음을 모두 갱신합니다.

- 반송파 도플러
- I 코드 주파수
- Q 코드 주파수
- 코드 위상
- 항법 심볼 위치
- secondary/tertiary code 위치

구현: LANS-AFS-SIM-main/afs_sim.c:867

따라서 위성별 신호는 PRN만 다른 것이 아니라, 거리 지연과 도플러도 서로 다릅니다.

## 6. I/Q 샘플 합성

각 샘플에서 위성별 신호는 대략 다음 식으로 생성됩니다.

I_data  = I 확산코드 × 항법 데이터
Q_pilot = Q 확산코드 × secondary × tertiary

output_I = gain × (I_data cosφ − Q_pilot sinφ)
output_Q = gain × (I_data sinφ + Q_pilot cosφ)

여기서 φ에는 위성별 반송파 도플러가 누적됩니다.

삼각함수는 매번 sin()과 cos()를 호출하지 않고, 512개 원소의 정수 lookup table을 사용합니다.

각 위성의 신호를 별도 버퍼에 만든 후 모든 위성을 더합니다.

## 7. 신호 세기와 잡음

거리 기반 이득은 다음처럼 적용됩니다.

path_loss = 5200000.0 / rho.range;

즉, 기준 거리 5,200 km 대비 1/range 진폭 모델입니다. 전력 기준으로 보면 대략 자유공간 손실의 1/r² 관계를 의도한 것입니다.

2비트 모드에서는 xorshift32 난수 발생기와 6개 균등분포 합산 방식으로 근사 가우시안 잡음을 생성합니다.

구현: LANS-AFS-SIM-main/afs_rand.c:21

잡음 크기는 샘플링 주파수와 위성 수에 따라 조정됩니다.

ADC 출력 레벨은 다음 네 값입니다.

-3, -1, +1, +3

주의할 점은 비트 패킹된 진짜 2비트 파일이 아니라 각 I와 Q 성분을 하나의 signed char로 저장한다는 것입니다.

## 8. 출력 파일 형식

출력은 헤더 없는 raw 복소 I/Q 스트림입니다.

### 기본 16비트 모드

int16 I, int16 Q, int16 I, int16 Q, ...

- 복소 샘플당 4바이트
- 12 MHz에서 초당 약 48 MB
- 300초면 약 14.4 GB

### -b 2 모드

int8 I, int8 Q, int8 I, int8 Q, ...

- 각 값은 -3/-1/+1/+3
- 복소 샘플당 2바이트
- 12 MHz에서 초당 약 24 MB
- 300초면 약 7.2 GB

파일 이름 대신 -를 주면 binary I/Q를 stdout으로 출력합니다.

## 9. 명령행 옵션

코드가 실제로 처리하는 옵션은 다음과 같습니다.

afs_sim [-t seconds]
[-s sample_rate]
[-e almanac_file]
[-b 2]
[-l latitude:longitude:height]
[-InQ]
output_file

- -t: 생성 시간, 기본 300초
- -s: 복소 샘플링 주파수, 기본 12 MHz
- -e: 알마낙 파일
- -b 2: 2비트 ADC 레벨을 int8로 출력
- -l: 달 표면 수신기 위치
- -InQ: MAX2771 출력을 흉내 내기 위해 Q 부호 반전
- 출력 파일 -: stdout 사용

파일 입력 경로는 실행 파일 위치가 아니라 현재 작업 디렉터리를 기준으로 찾습니다. 따라서 기본 데이터 파일이 있는 LANS-AFS-SIM-main 안에서 실행하는 것이 안전합니다.

## 10. SDR 재생 코드

player 폴더는 생성된 파일을 실제 SDR 장비로 재생하기 위한 별도 도구입니다.

- bladeRF: 재생 스크립트
- LimeSuiteNG: LimeSDR 설정 및 재생 스크립트
- limeplayer: LimeSuite API를 이용한 스트리밍 송신기

limeplayer는 파일 읽기 스레드와 송신 스레드 사이에 링 버퍼를 두고 LMS_SendStream()으로 데이터를 보냅니다.

다만 기본값은 다음과 같습니다.

TX_FREQUENCY  = 2492.028 MHz
TX_SAMPLERATE = 12 MHz

LANS-AFS-SIM-main/player/limeplayer/limeplayer.c:25

반면 현재 afs_sim은 DEMO_L1이 켜져 있어 1575.42 MHz 신호 모델입니다. 따라서 기본 설정끼리는 중심주파수가 서로 맞지 않습니다. 실제 송출 시 시뮬레이터 모드 또는 플레이어 주파수를 맞춰야 합니다.

또한 limeplayer는 16비트 I/Q 구조체를 읽으므로 afs_sim -b 2 출력과 바로 호환되지 않습니다.

## 11. 사용 라이브러리의 역할

- rtklib: 전체 GNSS 처리 엔진으로 사용되는 것이 아니라 사실상 CRC-24Q 등 일부 공통 함수에 사용
- pocketsdr: 비트 pack/unpack, LFSR, bit reversal
- ldpc: sparse parity-check 행렬 연산
- OpenMP: 위성별 신호 생성과 샘플 합산 병렬화
- LimeSuite: 생성 파일을 LimeSDR로 송출

즉, 수신·추적·항법해 계산 기능은 없습니다. 이 프로그램은 송신 신호 생성 전용입니다.

## 12. 코드에서 확인된 중요한 제한 및 문제

### 1. Subframe 3과 4는 시험 패턴

실제 항법 또는 서비스 메시지가 아니라 0101... 패턴입니다. 따라서 물리계층 검증에는 사용할 수 있지만 완전한 AFS 메시지 기능 검증에는 부족합니다.

### 2. Subframe 2가 시뮬레이션 중 갱신되지 않음

12초마다 갱신되는 것은 Subframe 1의 TOI뿐입니다. Week, ITOW와 ephemeris가 들어 있는 Subframe 2는 시작할 때 한 번 만들어지고 같은 내용이 계속 반복됩니다.

긴 시간 시뮬레이션에서는 송신 시각 정보의 일관성이 깨질 수 있습니다.

### 3. 16비트 모드에는 열잡음이 없음

잡음 추가 코드는 nbits == 2 분기에만 있습니다. 기본 16비트 모드는 위성 신호를 합산할 뿐 잡음을 추가하지 않습니다.

따라서 코드 주석의 C/N0 보정은 2비트 모드에만 적용됩니다.

### 4. OpenMP 반송파 lookup index 경쟁 조건

위성별 병렬 루프에서 ph 변수가 private 목록에 없습니다.

- 병렬 루프: LANS-AFS-SIM-main/afs_sim.c:1281
- 공유될 수 있는 ph 쓰기: LANS-AFS-SIM-main/afs_sim.c:1304

여러 스레드가 동시에 ph를 덮어쓸 수 있어 다른 위성의 반송파 위상 인덱스를 사용할 가능성이 있습니다.

### 5. 난수 발생기도 thread-safe하지 않음

2비트 ADC 루프가 OpenMP 병렬인데 randn()은 전역 rng_state를 수정합니다.

- 병렬 호출: LANS-AFS-SIM-main/afs_sim.c:1367
- 공유 RNG 상태: LANS-AFS-SIM-main/afs_rand.c:7

이는 데이터 경쟁이며, 결과 재현성과 잡음 통계에 영향을 줄 수 있습니다.

### 6. 알마낙 PRN 범위 검사 오류

if (sv < 0 || sv > MAX_SAT)

여기서는 sv >= MAX_SAT이어야 합니다.

현재 코드는 ID 13을 내부 인덱스 12로 받아들여 12개 배열의 바깥에 쓸 수 있습니다.

위치: LANS-AFS-SIM-main/afs_sim.c:681

### 7. 궤도 모델이 단순화됨

알마낙에서 Rate of Right Ascen을 읽어 넘기지만 저장하거나 계산에 사용하지 않습니다. 달 자전이나 달 고정좌표계 회전도 모델링하지 않고 수신기 좌표를 고정합니다.

따라서 장시간 정밀 궤도·도플러 시뮬레이션보다는 신호 포맷과 수신기 획득/추적 시험에 더 적합합니다.

### 8. 요청 시간보다 0.1초 짧게 출력

nsim = (int)((tsec - 0.1) * 10.0);

따라서 기본 300초를 요청하면 실제 생성 루프는 299.9초 분량입니다.

### 9. Tertiary 파일의 완전성을 검사하지 않음

readTertiary()가 한 줄 이상 읽기만 하면 성공으로 처리합니다. 210개 PRN 데이터가 모두 읽혔는지는 확인하지 않습니다.

### 10. 시간 rollover 처리가 불완전함

TOI를 단순히 증가시키며 적절한 범위 rollover와 함께 ITOW/Subframe 2를 갱신하지 않습니다. 12초 프레임을 많이 생성하면 항법 시간 필드 간 불일치가 생길 수 있습니다.

## 현재 소스 기준 정밀 확인표

앞 설명을 회의에서 정확하게 사용할 수 있도록 현재 함수와 배열 조작을 다시 대조한 결과다.

### AFS 프레임의 정확한 길이

| 영역 | 길이 | 프레임 index |
|---|---:|---:|
| SP | 68심볼 | 0~67 |
| SB1 | 52심볼 | 68~119 |
| interleaved SB2~SB4 | 5880심볼 | 120~5999 |
| 합계 | 6000심볼 | 0~5999 |

SB2~SB4의 interleaving 전 배열은:

```text
SB2 2400 + SB3 1740 + SB4 1740 = 5880
```

이다. 6000심볼 × 2 ms = 12초다.

### SP의 실제 값

`afs_sim.c`에 다음 값이 직접 하드코딩되어 있다.

```c
{0xCC, 0x63, 0xF7, 0x45, 0x36, 0xF4, 0x9E, 0x04, 0xA0}
```

마지막 byte의 상위 4bit까지만 사용해 총 68bit다. 모든 PRN이 같은 SP를 쓴다.

### SB1의 실제 입력과 출력

`generate_BCH_AFS_SF1(syms, fid, toi)`의 입력은:

```c
data = (fid << 7) | toi;
```

형태의 9bit다. 현재 호출은 항상 FID 0과 다음 frame의 `afst.toi + 1`이다. 이 9bit를 그대로 반복해 52bit로 만드는 것이 아니라:

1. 하위 8bit를 reverse하여 LFSR 초기값으로 사용
2. `0x9F` 인자로 51개 값을 생성
3. 9번째 bit를 첫 symbol과 나머지 symbol 극성에 반영

하여 52개의 0/1 symbol을 만든다. 함수명과 주석은 BCH라고 부르지만, 코드만으로 공식 BCH code parameter를 추가 단정하지 않는다.

### SB2의 어느 부분이 실제 값이고 어느 부분이 0101인가

CRC 입력 1176bit 전체를 먼저 `j % 2`로 채운 후 앞 284bit만 실제 시간·궤도·시계 값으로 덮는다.

| 위치 | 길이 | 실제 값 |
|---:|---:|---|
| 0~12 | 13 | WN |
| 13~21 | 9 | ITOW |
| 22~37 | 16 | toe / 16초 |
| 38~69 | 32 | eccentricity / 2^-32 |
| 70~101 | 32 | sqrt(A) / 2^-19 |
| 102~133 | 32 | inclination / (2^-31·π) |
| 134~165 | 32 | RAAN / (2^-31·π) |
| 166~197 | 32 | argument of perigee / (2^-31·π) |
| 198~229 | 32 | mean anomaly / (2^-31·π) |
| 230~245 | 16 | toc / 16초 |
| 246~267 | 22 | af0 / 2^-31 |
| 268~283 | 16 | af1 / 2^-43 |
| 284~1175 | 892 | 덮지 않은 `010101...` 시험 패턴 |
| 1176~1199 | 24 | 계산한 CRC24Q |

따라서 SB2 전체가 하드코딩은 아니다. 위성별 알마낙 때문에 앞 284bit는 위성마다 다르고, 뒤 892bit만 시험 패턴이다. `01010101`을 16진수로 묶으면 `0x55`라 로그에 `555555...`가 나타난다.

SB2는 시작할 때 위성별로 한 번 만들고 이후 갱신하지 않는다. SB1 TOI만 12초마다 갱신한다.

### SB3/SB4의 846bit

현재 소스의 직접 실행문은 다음과 같다.

```c
for (i = 0; i < 846; i++) syms[i] = i % 2;
```

- SB3 payload는 846bit `010101...`
- CRC24를 붙여 870bit
- SB4도 같은 `syms`를 그대로 사용
- 같은 LDPC 함수와 같은 입력이므로 현재 SB3/SB4 결과도 동일

846은 코드에서 정한 CRC 제외 payload 길이다. 846 + CRC24 = 870이고, LDPC에는 zero filler 10bit를 붙여 880bit systematic 입력을 사용한다.

### CRC24Q의 정확한 처리

`append_CRC24()`는 RTKLIB의 `rtk_crc24q()`를 호출한다.

- SB2: 1176bit payload + 24bit CRC = 1200bit
- SB3/SB4: 846bit payload + 24bit CRC = 870bit

CRC는 오류를 수정하지 않고 오류가 남았는지 검출한다. 오류 정정은 LDPC가 담당한다.

### LDPC 2차원 배열의 정체

`SF2_A_ind`, `SF2_B_Inv_ind`, `SF2_C_ind`, `SF2_D_ind`와 SF3 대응 배열의 각 `{행, 열}`은 sparse binary matrix에서 값 1인 위치다. payload 목록이 아니다.

SB2:

```text
systematic 1200 + p1 480 + p2 4560 = 전체 6240
전송 = systematic[240..1199] 960 + p1 480 + p2[0..959] 960
     = 2400심볼
```

SB3/SB4:

```text
payload+CRC 870 + filler 10 = systematic 880
systematic 880 + p1 352 + p2 3344 = 전체 4576
전송 = systematic[176..869] 694 + p1 352 + p2[0..693] 694
     = 1740심볼
```

전송하지 않는 위치를 제거하는 과정이 천공이다.

### interleaver의 실제 index

```c
for (i = 0; i < 98; i++)
    for (j = 0; j < 60; j++)
        out[k++] = in[j * 98 + i];
```

입력 5880심볼을 60×98 형태로 보고 열 방향 순서로 꺼내 연속 오류를 흩는다.

## 현재 코드에서 직접 확인된 추가 주의점

1. `chan[i].I.data[0]`만 실제 송신에 사용하며 두 frame buffer를 교대하지 않는다.
2. visible satellite 선택은 시작할 때 한 번이다.
3. almanac의 Rate of Right Ascen 값은 읽어서 건너뛰고 저장하지 않는다.
4. 달을 고정 반지름 구로 취급한다.
5. `nsim = (int)((tsec - 0.1)*10)`이라 요청 시간보다 0.1초 짧은 loop 수다.
6. 열잡음은 `nbits == 2`일 때만 추가한다.
7. 위성 OpenMP loop의 `ph`는 private 목록에 없어 공유 접근 가능성이 있다.
8. 2bit 병렬 loop에서 전역 RNG 상태를 쓰므로 동시 접근 가능성이 있다.
9. almanac index 검사가 `sv > MAX_SAT`라서 `sv == 12`를 차단하지 못한다.
10. tertiary reader는 필요한 모든 PRN 행이 완전한지 검사하지 않는다.
11. `limeplayer` 기본 주파수 2492.028 MHz는 현재 DEMO_L1 1575.42 MHz와 다르다.
12. `limeplayer`는 16bit I/Q를 읽으므로 `-b 2` 출력과 직접 맞지 않는다.
13. 현재 `afs_nav.c` 앞부분의 한글 비교 로그 일부는 문자열 따옴표가 손상되어 원본 makefile 직접 build가 실패할 수 있다. WPF용 `build-wsl.ps1`은 원본을 수정하지 않고 staging 복사본의 선택적 로그 함수만 비활성화하여 DLL을 만든다.

## 회의용 빠른 답변

- **이 프로그램의 입력/출력은?** almanac·옵션 입력, raw I/Q 출력이다.
- **프레임만 만드는가?** 내부에서 프레임을 만든 뒤 PRN 확산·도플러·I/Q 변조까지 한다.
- **왜 6000심볼인가?** 68+52+2400+1740+1740이며 symbol당 2 ms라 12초다.
- **SB1 9bit가 52symbol인가?** 그렇다. LFSR 기반 생성 절차를 거쳐 52symbol이 된다.
- **SB3/SB4에 각각 846bit인가?** 그렇고 현재 두 payload는 동일한 0101 시험 패턴이다.
- **CRC24는 24bit 추가인가?** 그렇다. 오류 검출용이다.
- **큰 2차원 배열은?** LDPC sparse matrix의 좌표다.
- **5555 로그 이유는?** 01010101 = 0x55이기 때문이다.
- **무엇을 안 하는가?** 수신 획득·추적, LDPC 복호, CRC 판정, 수신 PVT는 하지 않는다.


둘 다 일부 존재하지만, 주기능은 AFS I/Q 생성입니다.

정확히 말하면 프로그램 내부에 AFS 데이터 프레임을 구성하고 채널 코딩하는 변환 로직이 있으며, 그 결과를 확산·변조하여 최종 I/Q 샘플로 출력합니다.

궤도/시간 정보
→ AFS 데이터 비트 구성
→ CRC/BCH/LDPC
→ 인터리빙
→ 6000-symbol AFS 프레임
→ PRN 확산 및 I/Q 변조
→ raw I/Q 파일

### 하지만 범용 “AFS 프레임 변환기”는 아님

외부의 임의 AFS 데이터를 입력받아 프레임으로 바꾸는 인터페이스는 없습니다. 예를 들어 다음 기능은 없습니다.

- 바이너리/JSON 메시지를 AFS 프레임으로 변환
- 이미 만들어진 AFS 프레임을 읽어 재인코딩
- AFS 프레임만 별도 파일로 출력
- 수신 I/Q에서 AFS 프레임을 복호화
- LDPC 디코딩이나 CRC 검사
- 완전한 SF3/SF4 메시지 생성

현재 SF3와 SF4의 payload는 실제 데이터가 아니라 0101... 시험 패턴입니다. SF2도 시간·ephemeris 외 나머지 영역은 시험 패턴으로 초기화됩니다.

따라서 가장 정확한 표현은:

> AFS 프레임 생성·채널 인코딩 로직을 내부적으로 포함한 AFS I/Q 신호 생성기입니다.

AFS 프레임 변환 로직은 I/Q를 만들기 위한 중간 단계로 들어가 있을 뿐, 독립적인 변환 도구로 노출되어 있지는 않습니다. 다만 generate_BCH_AFS_SF1(), eph2sbf(), append_CRC24(), encode_LDPC_AFS_*(), interleave_AFS_SF234()를 분리하면
AFS 프레임 생성 라이브러리로 재사용할 수 있습니다.



CRC24
오류 검출

LDPC
오류 정정용 패리티 생성

Puncturing
전체 LDPC 코드워드 중 일부만 전송해 전송량 감소

Interleaving
연속 오류를 여러 위치로 분산

BPSK/확산/IQ 생성
완성된 6000심볼을 실제 신호 샘플로 변환
