# bladeRF 소스 코드 상세 설명

## 작성 기준

이 문서는 현재 폴더에 포함된 source, 공개 header, CMake 설정, CLI 구현·도움말, 예제와 라이선스 파일을 직접 대조해 작성했다. 동봉 README에서만 확인되는 빌드 환경 이력은 “README 기재 내용”으로 구분했고, 연결된 실제 장치 없이는 확정할 수 없는 최대 주파수·sample rate·gain 같은 hardware 성능값은 적지 않았다. `LnisAfsValidator` 적용 여부는 이 저장소의 애플리케이션 source와 project 참조를 검색한 결과를 기준으로 했다.

## 1. 한 문장 요약

`bladeRF-master`는 Nuand의 bladeRF 소프트웨어 정의 무선(SDR) 장치를 제어하기 위한 전체 플랫폼 소스다. PC에서 사용하는 `libbladeRF`와 `bladeRF-cli`, Cypress FX3 USB 펌웨어, FPGA HDL, 장치별 RF 제어 코드와 예제를 함께 포함한다.

이 소스 자체가 AFS 프레임을 만들거나 복호하는 것은 아니다. 이미 생성된 복소 I/Q 샘플을 RF로 송신하거나, 안테나에서 받은 RF를 복소 I/Q 샘플로 수집하는 하드웨어 입출력 계층이다.

## 2. 이 프로젝트에서의 정확한 위치

현재 저장소의 구성 요소를 역할별로 나누면 다음과 같다.

| 구성 요소 | 역할 |
|---|---|
| `LnisAfsValidator` | `.graw`를 AFS 6000심볼 프레임으로 만들고 UDP로 전송하며, 반대편에서 복호·복원·판정 |
| `LANS-AFS-SIM` | 궤도·AFS 프레임·PRN 확산·도플러를 포함한 기저대역 I/Q 시험 신호 생성 |
| `PocketSDR-AFS` | I/Q 입력에서 AFS 신호 획득·추적·프레임 복호·PVT 수행 |
| `bladeRF` | I/Q 샘플과 실제 RF 사이를 연결하는 SDR 장치 제어 및 스트리밍 |

관계를 단순화하면 다음과 같다.

```text
RF 송신 시험

.graw 또는 항법 데이터
        ↓
AFS 프레임·CRC·LDPC·인터리빙
        ↓
PRN 확산·반송파 변조·I/Q 샘플 생성
        ↓
bladeRF-cli 또는 libbladeRF
        ↓
USB → FX3 펌웨어 → FPGA → RF 송수신 칩
        ↓
안테나/RF 출력
```

```text
RF 수신 시험

안테나/RF 입력
        ↓
RF 송수신 칩 → FPGA → FX3 펌웨어 → USB
        ↓
libbladeRF 또는 SoapyBladeRF
        ↓
복소 I/Q 샘플
        ↓
PocketSDR-AFS의 획득·추적·AFS 복호
```

중요한 구분:

- `.graw` 파일은 GNSS 관측 레코드이지 I/Q 파형이 아니므로 bladeRF에 직접 송신할 수 없다.
- 현재 앱의 UDP 데이터그램은 6000개 AFS 이진 심볼을 패킹한 시험 전송 형식이지 bladeRF용 샘플 스트림이 아니다.
- bladeRF를 현재 앱에 연결하려면 AFS 심볼 뒤에 PRN 확산, 기저대역 변조, 샘플링과 SC16 Q11 변환 단계가 추가로 필요하다.
- 현재 애플리케이션 코드에는 `libbladeRF`, `bladeRF-cli` 또는 bladeRF DLL을 호출하는 경로가 없다. 이 폴더는 현재 참고·향후 연동용 오픈소스다.

## 3. 소스 스냅샷과 버전 식별

폴더 이름은 `bladeRF-master`이므로 브랜치 이름만 알 수 있다. 이 복사본 안에는 독립적인 `.git` 이력이 없어서 정확한 원본 commit hash와 취득 일자는 소스만으로 확인할 수 없다.

다만 현재 코드에서 확인되는 libbladeRF 버전은 다음과 같다.

| 항목 | 현재 소스 값 | 위치 |
|---|---:|---|
| libbladeRF major | 2 | `host/libraries/libbladeRF/CMakeLists.txt` |
| libbladeRF minor | 6 | 같은 파일 |
| libbladeRF patch | 1 | 같은 파일 |
| API version | `0x02060100` | `host/libraries/libbladeRF/include/libbladeRF.h` |

따라서 이 문서는 현재 포함된 `libbladeRF 2.6.1` API 소스를 기준으로 작성한다. 재현 가능한 오픈소스 기준점을 만들려면 별도로 원본 저장소 URL, commit hash 또는 release tag, 취득 일자를 기록해야 한다.

## 5. 전체 하드웨어·소프트웨어 데이터 경로

### 송신

```text
사용자 I/Q 버퍼 또는 I/Q 파일
  → bladeRF-cli / 사용자 프로그램
  → libbladeRF 동기식 또는 비동기식 스트림
  → libusb 또는 Windows CyAPI backend
  → USB bulk transfer
  → FX3 firmware
  → FPGA sample pipeline
  → DAC/RF transceiver
  → TX 커넥터
```

### 수신

```text
RX 커넥터
  → RF transceiver/ADC
  → FPGA sample pipeline
  → FX3 firmware
  → USB bulk transfer
  → libusb 또는 Windows CyAPI backend
  → libbladeRF
  → 사용자 I/Q 버퍼 또는 파일
```

각 계층의 책임은 다르다.

- RF transceiver는 주파수 변환, gain, analog bandwidth와 ADC/DAC를 담당한다.
- FPGA는 디지털 샘플 경로, timestamp, trigger, packet 처리와 사용자 logic을 담당한다.
- FX3는 PC와 FPGA 사이의 USB 제어 및 고속 데이터 전달을 담당한다.
- libbladeRF는 장치 검색, 설정, FPGA/firmware 관리와 샘플 스트리밍 API를 제공한다.
- bladeRF-cli는 libbladeRF 기능을 명령행과 script로 사용할 수 있게 한다.

## 6. bladeRF 세대별 코드 분리

`host/libraries/libbladeRF/src/board/`에는 `bladerf1`과 `bladerf2`가 별도로 구현되어 있다.

| 코드 경로 | 대표 하드웨어 계열 | RF 제어 코드에서 확인되는 칩 |
|---|---|---|
| `board/bladerf1/` | bladeRF x40/x115 계열 | LMS6002D |
| `board/bladerf2/` | bladeRF 2.0 micro xA4/xA5/xA9 계열 | AD9361 계열 |

공통 공개 API는 같아도 지원 채널 수, 주파수·sample rate·bandwidth·gain 범위, RF port, loopback과 trigger 기능은 장치별로 다를 수 있다. 응용 프로그램은 숫자를 하드코딩하기보다 다음 range 조회 API로 연결된 장치의 실제 범위를 확인하는 편이 안전하다.

- `bladerf_get_frequency_range()`
- `bladerf_get_sample_rate_range()`
- `bladerf_get_bandwidth_range()`
- `bladerf_get_gain_range()`

`BLADERF_CHANNEL_RX(n)`과 `BLADERF_CHANNEL_TX(n)`은 방향과 채널 번호를 함께 표현한다. bladeRF 2 계열 코드에는 RX0/RX1과 TX0/TX1 처리가 있으므로 X2 layout을 통한 MIMO도 지원하지만, 실제 사용 가능 여부는 장치와 FPGA image를 함께 확인해야 한다.

## 7. libbladeRF의 역할과 주요 파일

`host/libraries/libbladeRF`가 일반 응용 프로그램에서 가장 직접적으로 사용하는 부분이다.

| 파일·폴더 | 역할 |
|---|---|
| `include/libbladeRF.h` | 장치 독립 공개 C API, 구조체, enum, 스트림 형식 |
| `include/bladeRF1.h` | bladeRF 1 전용 및 일부 legacy API |
| `include/bladeRF2.h` | bladeRF 2 전용 API |
| `src/bladerf.c` | 공개 API를 장치별 함수로 전달하는 중심 구현 |
| `src/init_fini.c` | 라이브러리 초기화·종료 |
| `src/backend/` | USB backend 선택과 공통 interface |
| `src/backend/usb/libusb.c` | libusb 기반 구현 |
| `src/backend/usb/cyapi.c` | Windows Cypress CyAPI 기반 구현 |
| `src/board/bladerf1/` | bladeRF 1 초기화·설정·스트리밍 |
| `src/board/bladerf2/` | bladeRF 2 초기화·설정·스트리밍 |
| `src/streaming/` | 동기/비동기 버퍼와 transfer 상태 관리 |
| `src/helpers/` | config, interleave 등 보조 기능 |
| `doc/examples/` | 동기 RX/TX, metadata timestamp, sweep 등의 C 예제 |

일반적인 송신 프로그램의 호출 순서는 다음과 같다.

1. `bladerf_open()` 또는 장치 문자열을 사용하는 open API로 장치를 연다.
2. 장치·firmware·FPGA 상태와 버전을 확인한다.
3. `bladerf_set_frequency()`로 TX 중심주파수를 설정한다.
4. `bladerf_set_sample_rate()`로 복소 sample rate를 설정한다.
5. `bladerf_set_bandwidth()`와 `bladerf_set_gain()`을 설정한다.
6. `bladerf_sync_config()`로 TX layout, sample format, buffer 수와 timeout을 설정한다.
7. `bladerf_enable_module(..., true)`로 TX 경로를 활성화한다.
8. `bladerf_sync_tx()`에 I/Q sample buffer를 반복 전달한다.
9. 마지막 sample 처리 후 TX를 비활성화하고 `bladerf_close()`를 호출한다.

수신은 같은 구조에서 RX channel과 `bladerf_sync_rx()`를 사용한다.

공개 헤더의 오류 코드 규칙은 음수이면 실패, 0 이상이면 성공이다. 각 단계의 반환값을 검사하고 `bladerf_strerror()`로 원인을 남겨야 장치 없음, timeout, USB 오류, 범위 오류와 FPGA 미구성을 구분할 수 있다.

## 8. 스트리밍 방식

### 동기식 API

`bladerf_sync_config()`, `bladerf_sync_tx()`, `bladerf_sync_rx()`는 내부 비동기 transfer를 라이브러리가 관리하면서 호출자에게 blocking 형태의 간단한 API를 제공한다. 파일 재생기나 단일 producer/consumer 구조에는 이 방식이 가장 단순하다.

`bladerf_sync_config()`의 주요 값:

| 인자 | 의미 |
|---|---|
| channel layout | RX/TX와 X1/X2 채널 구성 |
| format | sample 형식과 metadata 사용 여부 |
| num buffers | 내부 순환 buffer 개수 |
| buffer size | buffer 하나의 sample 수 |
| num transfers | 동시에 진행할 USB transfer 수 |
| timeout | stream operation 제한시간 |

예제 `doc/examples/sync_rxtx.c`는 buffer 16개, transfer 8개를 사용한다. `sync_tx_meta.c`는 buffer 32개, transfer 16개를 사용한다. 이 값은 모든 환경의 정답이 아니라 예제이며, sample rate, USB controller, 처리 지연과 OS scheduler에 맞춰 측정해야 한다.

### 비동기식 API

낮은 수준의 stream API는 callback과 사용자 buffer를 사용한다. 지속적인 고속 처리, 자체 buffer pool 또는 특정 latency 제어가 필요할 때 유용하지만 상태 전이와 종료 처리가 동기식 API보다 복잡하다.

현재 AFS 시험용 파일을 순차 재생하는 첫 연동이라면 동기식 TX가 더 단순하다. 실시간으로 12초 프레임을 계속 합성하여 송신하고 buffer underrun을 정밀 관리해야 할 때 비동기식 전환을 검토할 수 있다.

## 9. I/Q sample 형식

### SC16 Q11

bladeRF-cli의 기본 binary 형식과 대표 libbladeRF 형식은 `BLADERF_FORMAT_SC16_Q11`이다.

```text
I0(int16), Q0(int16), I1(int16), Q1(int16), ...
```

- 각 I와 Q는 right-aligned little-endian `int16_t`다.
- CLI 문서가 안내하는 DAC sample 범위는 `-2048~2047`이다.
- binary 파일에는 별도 header, sample rate, 중심주파수 또는 gain 정보가 없다.
- 파일을 재생할 때 sample rate와 RF 설정을 별도로 동일하게 지정해야 한다.

`BLADERF_FORMAT_SC16_Q11_META`는 sample 데이터에 timestamp와 상태 정보를 결합하여 예약 시각 송신, timestamp 기반 수신 등에 사용한다. `BLADERF_FORMAT_SC16_Q11_PACKED`는 packed 전송 형식이다. 일반 형식과 packed 형식을 파일 크기만 보고 섞어 사용하면 안 된다.

현재 소스에는 SC8 Q7 관련 CLI 설명과 형식도 있지만 장치, FPGA, layout에 따른 지원 여부를 API와 연결 장치에서 확인해야 한다. AFS 기준 파일 형식을 정할 때는 형식 이름, channel 수, I/Q 순서, sample rate, 중심주파수, scaling을 시험 명세에 함께 기록해야 한다.

### LANS-AFS-SIM 출력과의 관계

LANS-AFS-SIM의 기본 16-bit 출력도 header 없는 interleaved `int16 I, int16 Q` 파일이고, 동봉된 다음 script가 이를 bladeRF-cli binary TX 입력으로 사용한다.

`LANS-AFS-SIM-main/player/bladeRF/bladerf_script.txt`:

```text
set frequency tx 2492.028M
set frequency rx 1575.42M
set samplerate 12M
set bandwidth 12M
set gain tx 0
tx config file=afssim_iq16.bin format=bin
tx start
```

그러나 단순히 container가 int16이라는 사실만으로 모든 값이 적절한 SC16 Q11 범위라는 뜻은 아니다. 송출 전에는 다음을 확인해야 한다.

- I/Q 값이 `-2048~2047`을 넘는지와 clipping 여부
- 파일의 I/Q 순서와 Q 부호
- simulator sample rate와 CLI sample rate 일치
- simulator가 가정한 신호 중심주파수와 bladeRF TX frequency 일치
- 파일 끝에서 반복할지, 1회 송신할지
- TX gain과 외부 감쇠기 적용값

특히 현재 LANS-AFS-SIM 소스는 `DEMO_L1` 설정으로 1575.42 MHz 신호를 모델링하지만 동봉 bladeRF script의 TX는 2492.028 MHz다. 그대로 실행하면 생성 모델과 실제 RF 중심주파수의 의미가 맞지 않는다. 사용하려는 AFS band를 먼저 정하고 simulator 설정과 TX frequency를 동일한 기준으로 맞춰야 한다.

LANS-AFS-SIM의 `-b 2` 출력은 I와 Q를 각각 `int8`로 기록하므로 SC16 Q11 binary로 그대로 취급할 수 없다. SC16 Q11로 변환·scaling하거나 지원되는 정확한 8-bit stream 형식을 별도로 구성해야 한다.

## 10. bladeRF-cli

`host/utilities/bladeRF-cli`는 장치 확인, 설정, FPGA/firmware 관리와 I/Q 파일 송수신에 사용하는 도구다.

대표 명령:

| 명령 | 역할 |
|---|---|
| `bladeRF-cli -p` | 연결 장치 목록 확인 |
| `bladeRF-cli -e info -e version` | 장치, firmware, FPGA, library 정보 확인 |
| `bladeRF-cli -f <firmware>` | firmware flash |
| `bladeRF-cli -l <fpga.rbf>` | FPGA image load |
| `bladeRF-cli -i` | interactive mode 시작 |
| `bladeRF-cli -s setup.txt` | CLI script 실행 |
| `set frequency ...` | RX/TX 중심주파수 설정 |
| `set samplerate ...` | sample rate 설정 |
| `set bandwidth ...` | analog/filter bandwidth 설정 |
| `set gain ...` | gain 설정 |
| `rx config` / `tx config` | 파일, 형식, sample 수, 반복, buffer 구성 |
| `rx start` / `tx start` | background stream 시작 |
| `rx wait` / `tx wait` | script 종료 전에 stream 완료 대기 |

예를 들어 binary I/Q 파일 1회를 송신하는 최소 흐름은 다음과 같다.

```text
set frequency tx <시험 중심주파수>
set samplerate <파일 sample rate>
set bandwidth <필요 bandwidth>
set gain tx <안전하게 검토한 gain>
tx config file=<SC16Q11 파일> format=bin repeat=1
tx start
tx wait
```

장치가 여러 대면 serial number를 포함한 device selector를 사용해야 잘못된 장치를 여는 것을 막을 수 있다. `bladeRF-cli -p`로 serial을 먼저 확인한다.

CLI의 CSV TX는 내부에서 `bladeRF_samples_from_csv.bin` 임시 binary 파일로 변환한다. 대용량 AFS 파형에는 CSV가 느리고 크므로 검증용 소량 sample 외에는 binary가 적절하다.

## 11. FPGA와 FX3 firmware

### FX3 firmware

`fx3_firmware/`는 Cypress FX3 USB controller용 소스다. PC의 control 요청, USB endpoint와 FPGA 사이의 sample transport, 장치 초기화와 firmware recovery 경로를 담당한다.

host library와 FX3 firmware는 `firmware_common/`의 protocol 정의를 공유한다. 따라서 host, firmware와 FPGA 버전 조합이 호환되어야 한다. firmware update 중 장치를 분리하면 bootloader 상태로 들어갈 수 있으며 공식 README는 bladeRF-cli의 `recovery` 기능을 안내한다.

### FPGA HDL

`hdl/`에는 bladeRF 1과 bladeRF 2 플랫폼, 공통 IP와 software 자료가 있다. FPGA는 단순 통과선이 아니라 다음 기능의 일부를 맡는다.

- USB sample packet과 RF sample path 연결
- RX/TX FIFO와 흐름 제어
- timestamp와 metadata
- trigger와 다중 장치 동기
- GPIO, expansion과 RFIC control 연결
- 장치별 digital signal path

소스만 추가했다고 FPGA image가 자동으로 준비되는 것은 아니다. 대상 보드에 맞는 prebuilt image를 사용하거나 해당 toolchain으로 빌드하고, firmware·libbladeRF가 요구하는 호환 버전을 확인해야 한다.

## 12. 소스 빌드

### Host library와 CLI

현재 포함된 `host/README.md`가 제시하는 Linux/macOS 빌드 흐름은 다음과 같다.

```sh
cd host
mkdir -p build
cd build
cmake [options] ../
make
sudo make install
sudo ldconfig
```

필수 host 의존성은 CMake와 libusb 개발 파일이다. README에는 libusb 1.0.16 이상을 Linux에, 1.0.19 이상을 Windows에 권장한다고 적혀 있다. 이것은 현재 환경에서 다시 검증한 요구 버전이 아니라 이 복사본의 공식 README 기재 내용이다.

Windows는 `host`를 CMake source로, 별도 `host/build`를 build directory로 지정한 뒤 Visual Studio solution을 생성하는 절차가 적혀 있다. 포함 README는 Windows 10, CMake 3.9.0, libusb 1.0.21, Visual Studio 2017에서 마지막으로 확인했다고 명시하므로 최신 Windows/Visual Studio에서 그대로 보장된다고 단정할 수 없다.

Windows backend 선택:

| CMake 옵션 | 코드상 역할 |
|---|---|
| `ENABLE_BACKEND_LIBUSB` | libusb USB backend |
| `LIBUSB_PATH` | Windows에서 libusb 위치 지정 |
| `ENABLE_BACKEND_CYAPI` | Cypress CyAPI/CyUSB3.sys backend |
| `FX3_SDK_PATH` | CyAPI backend 빌드에 필요한 FX3 SDK 위치 |
| `ENABLE_BACKEND_DUMMY` | 개발용 dummy backend |

일반 애플리케이션 연동에 필요한 산출물은 libbladeRF shared library/DLL, 공개 header와 runtime 의존 DLL이다. FPGA와 FX3 firmware를 소스에서 직접 빌드하지 않는다면 `ENABLE_FX3_BUILD`는 기본 OFF 상태로 두고 호환되는 image를 별도로 준비한다.

### Git submodule

`.gitmodules`에는 다음 두 경로가 선언되어 있다.

- `thirdparty/analogdevicesinc/no-OS`
- `host/utilities/bladeRF-fsk`

master ZIP처럼 가져온 소스는 submodule 내용이 빠질 수 있다. 특정 board 또는 utility 빌드 전에 해당 디렉터리가 실제 소스를 포함하는지 확인해야 한다. 소스가 없는데 임의 버전을 섞으면 현재 snapshot과 호환된다고 보장할 수 없다.

## 13. Timestamp, trigger와 다중 장치 동기

공개 API는 metadata timestamp, 예약 retune, trigger와 장치 timestamp 조회 기능을 포함한다. `host/examples/bladeRF-cli/sync_trx` 예제는 두 장치를 다음과 같이 연결한다.

- 두 장치의 trigger pin 연결
- 두 장치의 ground 연결
- 한 장치의 38.4 MHz reference clock을 다른 장치에 공급
- master trigger와 slave trigger arm
- trigger fire 후 RX/TX 시작

예제 문서는 trigger가 sample 흐름을 gate하고 fire 시 여러 경로가 `±1 sample clock` 안에서 시작한다고 설명한다. 동시에 다음 한계도 직접 명시한다.

- 두 장치 mixer의 PLL은 독립이므로 sampling clock을 공유해도 RF phase가 자동 정렬된다고 보장하지 않는다.
- 장치별 phase offset은 고정될 수 있지만 별도 측정과 보정이 필요하다.
- TX에서 RX까지 고정 지연은 FPGA/RF chain과 FPGA version에 따라 달라질 수 있다.

따라서 AFS 단일 장치 송수신에는 일반 동기식 stream이면 충분할 수 있지만, 다중 송신기·수신기 시간 정렬 시험에서는 reference clock, trigger, timestamp와 고정 지연 보정이 모두 시험 조건에 들어가야 한다.

## 14. 오류와 성능 문제를 구분하는 기준

`libbladeRF.h`에 정의된 대표 오류는 다음과 같다.

| 오류 | 의미 |
|---|---|
| `BLADERF_ERR_RANGE` | 설정값이 장치 허용 범위를 벗어남 |
| `BLADERF_ERR_INVAL` | 잘못된 동작 또는 인자 |
| `BLADERF_ERR_IO` | 파일 또는 장치 I/O 실패 |
| `BLADERF_ERR_TIMEOUT` | 제한시간 안에 작업이 끝나지 않음 |
| `BLADERF_ERR_NODEV` | 사용할 장치가 없음 |
| `BLADERF_ERR_UNSUPPORTED` | 해당 장치/구성에서 미지원 |
| `BLADERF_ERR_UPDATE_FPGA` | FPGA update 필요 |
| `BLADERF_ERR_UPDATE_FW` | firmware update 필요 |
| `BLADERF_ERR_TIME_PAST` | 요청 timestamp가 이미 지남 |
| `BLADERF_ERR_PERMISSION` | 장치 접근 권한 부족 |
| `BLADERF_ERR_NOT_INIT` | 동작에 필요한 초기화 미완료 |

이 오류와 RF 품질 문제는 분리해서 봐야 한다.

- API가 성공해도 sample scale이 너무 크면 DAC clipping이 생길 수 있다.
- USB 전송이 간헐적으로 늦으면 TX sample 연속성이 깨질 수 있다.
- 중심주파수, sample rate 또는 I/Q 부호가 다르면 RF는 나오더라도 수신기가 AFS를 획득하지 못한다.
- gain과 bandwidth가 부적절하면 포화, 낮은 C/N0 또는 불필요한 대역 외 성분이 생길 수 있다.
- firmware, FPGA와 host library version 조합이 맞지 않으면 장치 초기화나 기능 호출 단계에서 실패할 수 있다.

실험 로그에는 최소한 다음 값을 함께 남겨야 재현할 수 있다.

```text
장치 serial과 board name
libbladeRF / firmware / FPGA version
USB backend와 USB speed
RX/TX channel과 RF port
중심주파수
실제 적용 sample rate
실제 적용 bandwidth
gain mode와 gain
sample format과 channel layout
buffer size, buffer 수, transfer 수와 timeout
송신 sample 수와 시작/종료 시각
모든 libbladeRF 오류 코드
```

## 15. 라이선스

최상위 `COPYING`이 명시하는 기본 라이선스는 구성 요소마다 다르다.

| 구성 요소 | `COPYING`의 라이선스 |
|---|---|
| FPGA HDL | MIT |
| FX3 firmware | MIT |
| libbladeRF | LGPL-2.1 |
| bladeRF-cli | GPL-2.0 |
| Linux kernel driver | GPL-2.0 |
| metadata와 build script | 별도 표기가 없으면 MIT |

추가 주의사항도 `COPYING`에 직접 적혀 있다.

- `host/common`과 `host/utilities/common`의 일부 파일은 파일별 라이선스가 다를 수 있다.
- `hdl/fpga/ip`의 FPGA IP는 각 IP별 라이선스가 다를 수 있다.
- 정확한 전문은 `legal/licenses/`와 개별 source header를 확인해야 한다.

따라서 이 폴더 전체를 하나의 단일 라이선스로 표기하면 부정확하다. 응용 프로그램에서 DLL 형태의 libbladeRF만 사용하는 경우와 GPL bladeRF-cli 소스를 제품에 포함·수정하는 경우도 배포 의무 검토 범위가 다르다. 실제 배포 전에는 포함 파일과 링크 방식을 기준으로 별도 오픈소스 고지와 법적 검토가 필요하다.

## 16. 현재 LnisAfsValidator와의 연동 상태

현재 애플리케이션 source와 project file을 검색한 결과, bladeRF 공개 header, DLL, NuGet/package, P/Invoke 또는 CLI 실행 코드는 없다. bladeRF 이름이 나타나는 곳은 현재 다음 참고 관계다.

- LANS-AFS-SIM README가 RF 변환용 SDR 예로 bladeRF를 언급
- LANS-AFS-SIM의 `player/bladeRF/bladerf_script.txt`
- PocketSDR 일반판이 SoapySDR 장치 중 bladeRF를 설명
- 이번에 추가한 원본 `bladeRF-master` 소스

따라서 현재 구현 상태를 정확히 표현하면 다음과 같다.

| 기능 | 현재 상태 |
|---|---|
| AFS 논리 프레임 UDP 송수신 | 구현됨 |
| `.graw` → AFS SB3/SB4 fragment | 구현됨 |
| AFS frame → PRN 확산 I/Q 실시간 변조 | 현재 앱에는 없음 |
| libbladeRF 직접 링크/P/Invoke | 없음 |
| bladeRF-cli process 제어 | 없음 |
| bladeRF TX/RX 상태를 UI에 표시 | 없음 |
| 실제 RF 종단 간 자동 시험 | 없음 |

현재 앱이 만든 750바이트 AFS frame packet을 `tx config file=...`로 보내면 올바른 RF AFS 신호가 되지 않는다. bladeRF TX 입력은 시간 순서의 복소 I/Q sample이어야 하며, 6000심볼 AFS frame은 먼저 data channel PRN code와 곱하고 sample rate에 맞춰 전개한 뒤 carrier/baseband I/Q로 변환해야 한다.

## 17. AFS RF 시험에 활용하는 현실적인 단계

소스 기준으로 가장 단순한 첫 검증은 현재 WPF 앱에 libbladeRF를 바로 넣는 것이 아니라 기존 I/Q 생성기와 CLI를 분리해 확인하는 방식이다.

1. LANS-AFS-SIM에서 짧은 16-bit I/Q 파일을 생성한다.
2. I/Q sample 최소·최대값과 SC16 Q11 범위를 확인한다.
3. simulator의 sample rate와 중심주파수 설정을 기록한다.
4. `bladeRF-cli -p`, `info`, `version`으로 장치와 세 버전을 기록한다.
5. dummy load나 RF 차폐·감쇠 환경에서 TX script의 주파수·sample rate·bandwidth·gain을 설정한다.
6. `tx start`, `tx wait`로 1회 재생하고 오류와 sample 연속성을 확인한다.
7. 수신 bladeRF에서 I/Q를 저장하고 PocketSDR-AFS가 신호를 획득·복호하는지 확인한다.
8. 파일 재생 경로가 검증된 뒤에만 libbladeRF 직접 연동 또는 실시간 waveform 생성을 설계한다.

직접 연동을 구현한다면 최소 경계는 다음처럼 분리하는 편이 현재 구조와 맞는다.

```text
AFS frame codec                    기존 역할
        ↓
AFS waveform generator             새 역할: PRN·I/Q·scaling
        ↓
I/Q sample source                  파일 또는 실시간 buffer
        ↓
bladeRF transport adapter          libbladeRF 호출만 담당
        ↓
장치
```

bladeRF transport가 AFS CRC·LDPC나 `.graw`를 알게 만들면 RF 장치 제어와 protocol 구현이 섞인다. 반대로 waveform generator가 장치 serial이나 USB buffer를 알 필요도 없다.

## 18. RF 송출 안전 주의

bladeRF가 API 호출을 허용한다고 해서 해당 주파수와 출력으로 전파를 방사해도 된다는 의미는 아니다. 실제 송신은 사용 지역의 전파 법규, 허가 주파수, 출력 제한과 시험장 규정을 따라야 한다.

초기 시험은 다음 조건이 안전하다.

- 안테나를 연결하지 않은 전도성 시험 구성
- 송수신기 사이에 계산된 충분한 고정 감쇠기 사용
- 장치 입력 허용 전력 확인
- 낮은 TX gain에서 시작
- spectrum analyzer 또는 power meter로 출력 확인
- 차폐함 또는 허가된 시험 환경 사용

소프트웨어 품질 시험과 RF 방사 허가는 별개의 문제다.

## 최종 평가

`bladeRF-master`는 AFS 규격 구현물이 아니라 실제 RF 하드웨어를 움직이는 범용 SDR platform source다. 이 프로젝트에서 사용할 수 있는 핵심은 `libbladeRF`의 장치 설정·I/Q stream API와 `bladeRF-cli`의 파일 재생·수집 기능이다.

현재 상태에서는 다음 표현이 정확하다.

> AFS 프레임 생성·복호는 현재 애플리케이션과 AFS 오픈소스가 담당하고, bladeRF 소스는 향후 그 위에 I/Q waveform 계층을 연결했을 때 실제 RF 송수신 장치 계층으로 사용할 수 있다.

bladeRF 소스를 폴더에 추가한 것만으로 현재 UDP 기반 AFS 시험이 RF 시험으로 바뀌지는 않는다. RF 종단 간 시험을 만들려면 sample 형식과 scaling, 중심주파수, sample rate, waveform 생성, 장치 버전 호환, 수신 I/Q 처리와 RF 안전 조건을 별도로 구현·검증해야 한다.
